# V2.1「入行第一年」产品与体验设计

- 状态：已批准方向，待书面规格复核
- 日期：2026-07-11
- 基线：`v2.0` / `e8d0cd0d00d69372ab56e7da7a11347b2bcc962a`
- 工作分支：`feat/v2.1-first-year-experience`
- 目标用户：中国程序员与技术从业者
- 产品形态：免费 Web 单机游戏，桌面优先且移动端完整可用

## 1. 第一性原理

V2.0 已经具备完整的模拟底座和大量内容：

- 4 条初始职业路径；
- 234 个行动；
- 1,593 个事件；
- 21 个结局；
- 8 个成就和 17 个商店物品；
- 每日挑战、人生脚本、结局复盘、分享卡、本地存档和三套主题；
- 22 个测试文件、225 项测试和 72 场景批量模拟门槛。

因此，当前主矛盾不是“内容不足”，而是玩家第一次进入后能否快速理解：

1. 我现在处于什么人生阶段；
2. 这一阶段最重要的目标是什么；
3. 某个选择为什么可用、为什么值得考虑；
4. 结果为什么发生；
5. 我是否愿意继续下一阶段或重新开一局。

V2.1 的北极星不是页面停留时长，而是：

> 玩家完成一段可解释的职业人生，并主动选择继续下一段或开启另一条路线。

V2.1 选择“入行第一年”作为最小闭环。它从第 0 月开始，到第 12 月复盘结束，覆盖作品集、投递、面试、Offer、入职和现金流管理，是玩家理解整套游戏因果关系的最短路径。

### 2.2 评价中反复出现的正面模式

1. **自动化产生掌控感**：玩家写下规则后，看系统自行运转，获得“这是我设计出来的”成就感。
2. **现实经验被重新理解**：人生模拟被喜欢，不是因为数值多，而是玩家在选择中看见自己、父母、工作和遗憾。
3. **阶段解锁承载学习曲线**：编程农场把排序、路径和算法映射为新的生产问题，学习内容与游戏目标一致。
4. **可复盘结果推动重玩**：玩家愿意比较不同路线、不同世代和不同策略的后果。

### 2.3 评价中反复出现的负面模式

1. 新手教程假设玩家已经懂系统，首局像阅读说明书；
2. 选项很多，但缺少当下目标，玩家不知道先做什么；
3. 中后期重复同一套最优操作，自动化退化为等待；
4. 剧情文本与真实状态矛盾，破坏因果可信度；
5. 多周目只有数值变化，没有路线身份和新问题；
6. 内容很多但无法跳过、筛选或理解，形成信息负担。

这些风险与当前产品直接相关：V2.0 新局默认打开“恢复放松”分类，自动基线平均第 9 月获得首份 Offer，单局基线可能在第 12 月进入现金流陷阱；同时启动页一次展示职业、城市、价值观、每日挑战和继续存档，游戏页首屏又暴露多个状态、工具和行动分类。

### 2.4 当前真实使用证据的限制

当前 Nginx 日志中，主 JavaScript 资源仅观察到 13 次浏览器请求、约 12 个来源 IP。该数据包含测试和验证流量，不能当作有效用户样本；GitHub 也没有可用的玩家 issue。

因此：

- V2.1 不依据当前流量做数值平衡结论；
- 先以竞品证据、现有模拟门槛和定向可用性验证修复首局；
- 暂不为极低流量部署独立分析平台；
- 已评估 Umami，其支持自托管、自定义事件和属性，但目前引入数据库、服务和运维成本大于收益；当有效会话达到 100 后重新评估。

参考：

- Umami 官方仓库：https://github.com/umami-software/umami
- Umami 事件文档：https://umami.is/docs/track-events

## 3. 路线比较与决策

### 路线 A：首局体验与节奏重构（采用）

优点：直接解决当前最大流失点；复用现有引擎和内容；不引入后端；风险可由现有测试覆盖。

代价：短期不会直接产生排行榜或社交增长，需要在发布后继续积累真实玩家样本。

### 路线 B：每日挑战在线化

包括账号、排行榜、服务端 seed 校验和在线分享。

拒绝原因：当前有效流量不足，在线系统会提前引入作弊、安全、隐私、数据库和运维成本，无法证明优先级。

### 路线 C：继续扩职业、事件和结局

拒绝原因：已有内容规模足够大，继续扩张会放大入口密度、重复操作和内容不可发现问题。

## 4. 产品目标与非目标

### 4.1 产品目标

1. 玩家在 45 秒内完成第一次有效行动；
2. 玩家始终能看到一个当前阶段目标和一个可解释的建议；
3. 标准首局在第 6-9 月进入 Offer 链路，与当前批量模拟实测范围一致；
4. 第 12 月形成一次不终止游戏的阶段复盘；
5. 玩家能理解至少一个收益、一个代价和一个错失机会；
6. 第一年的结束自然导向“继续职业生涯”或“换路线重开”。

### 4.2 明确不做

- 不新增行动、事件、职业和结局；
- 不修改工资、事件概率、Offer 概率或核心成长公式；
- 不增加账号、云存档、排行榜、多人玩法和付费；
- 不接入第三方分析脚本；
- 不让推荐系统替玩家自动执行行动；
- 不把普通模式改造成强制教程；
- 不改变每日挑战的确定性与现有结果记录；
- 不强制旧存档进入新的第一年流程。

## 5. 体验设计

### 5.1 启动与角色设置

启动页仍然是可直接使用的角色设置界面，不增加营销落地页。

调整：

1. 有存档时，“继续上次人生”保持第一主命令；
2. 新局设置保留四个职业，但压缩标题区和重复说明；
3. 城市与价值观合并为紧凑的“初始条件”区域；
4. 主要命令始终在首个桌面视口内可见，在移动端作为稳定的底部操作区；
5. “今日人生”降为次级命令，不与普通新局争夺相同视觉权重；
6. 主命令旁展示当前配置摘要，例如“产品界面工程师 · 二线 · 稳健成长”；
7. 不增加轮播式教程、功能说明卡或大段操作指引。

### 5.2 第一年的三个阶段

阶段由真实状态优先、月份兜底，不用月份硬锁玩家。

#### 阶段一：建立入场券

进入条件：新局且未拥有作品集。

核心目标：形成至少一个作品集项目，并保持现金和精神处于可继续求职的状态。

建议优先级：`project_practice` → `system_learning` → 合理恢复。

#### 阶段二：进入机会链

进入条件：已有作品集，但尚未就业。

核心目标：投递 → 当前有效面试 → 当前有效 Offer → 接受 Offer。

建议优先级复用现有 `autoChoiceSystem` 的机会优先逻辑：

- 当前有 Offer：`C2002`；
- 当前有面试：`J2003`；
- 可投递：`job_hunt`；
- 尚不可投递：`project_practice` 或 `system_learning`；
- 精神或健康危险时，恢复类行动拥有更高优先级。

#### 阶段三：站稳第一份工作

进入条件：已就业且未完成第一年复盘。

核心目标：保持正现金流，完成稳定交付，并避免用持续加班换取短期最优。

建议优先级：`regular_work`、必要恢复、基础成长；危机状态继续覆盖普通推荐。

### 5.3 第一年的目标带

游戏页在核心状态区和主内容区之间增加一条无嵌套卡片的目标带，包含：

- 当前阶段名称；
- 一个主目标；
- 3 个以内的真实进度节点；
- 一个建议行动及其原因；
- 已完成节点使用明确状态，不使用装饰性进度。

示例：

```text
入行进度  作品集 ✓  投递 2 次  面试 1 次  Offer 待获取
建议：参加面试｜当前机会将在本阶段失效，优先处理比继续刷技术更重要
```

这条目标带提供人生目标和因果信息，不出现“点击这里”“功能介绍”或键盘教学。

### 5.4 行动区

1. 初始行动分类由第一年阶段派生，不再固定为“恢复放松”；
2. 推荐行动仍位于原分类和原行动列表中，只增加一个低权重“建议”状态；
3. 推荐必须显示一句基于真实状态的理由；
4. 玩家手动切换分类后，本月内不强制跳回推荐分类；
5. 不可用行动继续显示真实门槛；
6. 推荐行动不可用时必须回退到当前第一个可执行行动，不能展示假建议；
7. 人生脚本不参与第一年推荐，也不自动接管首局。

### 5.5 工具降噪

游戏头部保留高频状态和命令，成就、商店、脚本、收藏、手动保存和换角色收敛为一个稳定的次级工具入口；撤销仅在可用时提升权重。

要求：

- 桌面和移动端不再用整块按钮网格占据首屏；
- 次级入口使用熟悉符号并具备可访问名称和 tooltip；
- 自动存档仍是默认行为，手动保存作为次级保险；
- 不删除任何现有能力。

### 5.6 第一年度复盘

普通新局在满足以下条件时展示一次：

- `month >= 12`；
- 未结束游戏；
- 没有待处理事件；
- 新局带有 V2.1 第一年度体验标记；
- 本局尚未确认过第一年度复盘。

复盘内容：

1. 第一年的路径摘要；
2. 作品集、投递、面试、Offer 和就业结果；
3. 现金、精神、健康、技术和 AI 的年度变化；
4. 决策日志中最重要的 3 个选择；
5. 一个做对的节奏；
6. 一个已形成的风险；
7. 下一阶段建议。

主命令为“继续职业生涯”，次命令为“换路线重开”。关闭或继续后写入幂等标记；时间轴允许以后重新打开报告。

第一年度复盘不是结局，不生成结局成就，不写每日挑战历史，也不改变后续引擎结果。

## 6. 技术设计

### 6.1 组件边界

`GameContainer.tsx` 当前实测为 440 行，已经同时承担状态、主屏和行动区。V2.1 不继续向该文件堆跨区域 UI 和弹窗编排。

计划边界：

- `src/components/GameContainer.tsx`
  - 只保留游戏状态、存档、弹窗编排和高层事件；
- `src/components/GameScreen.tsx`
  - 从现有文件行为保持地迁出游戏主屏；
- `src/components/FirstYearProgressBand.tsx`
  - 渲染阶段目标、节点和推荐；
- `src/components/dialogs/FirstYearReviewDialog.tsx`
  - 渲染第一年度复盘；
- `src/components/CareerSetupScreen.tsx`
  - 从 `App.tsx` 迁出并承载新局设置布局；
- `src/systems/firstYearExperienceSystem.ts`
  - 纯函数派生阶段、目标、建议和复盘数据；
- `src/tests/firstYearExperience.test.ts`
  - 覆盖纯系统规则；
- 现有 UI 契约和月度 UI 测试
  - 覆盖接线、旧存档、每日挑战和弹窗优先级。

不创建全局 Context，不引入状态管理库，不增加运行时依赖。

### 6.2 数据来源

第一年系统只读取现有数据：

- `career.portfolioCount`；
- `career.pendingApplications`；
- `career.scheduledInterviews`；
- `career.activeOffers`；
- `career.employmentStatus`；
- 新局初始配置中的职业 XP、现金、精神和健康基线；
- `decisionLog`；
- `turningPoints`；
- 可见属性和现金流派生值；
- `flags` 中的 V2.1 资格与复盘确认标记。

推荐行动复用 `chooseActionForStrategy(state, 'stable_cashflow')` 的机会与危机优先级，再由第一年系统补充产品化理由。系统不复制 Offer 判定、行动门槛或危机公式。

### 6.3 持久化和兼容

新建普通局写入：

```text
flags.v21_first_year_experience = true
```

确认第一年度复盘后写入：

```text
flags.v21_first_year_review_seen = true
```

使用现有 `flags`，不改变 `GameState` 类型结构，不新增存档迁移版本。

- 旧存档没有资格标记，不自动弹出新流程；
- 每日挑战不写资格标记；
- 新旗标不参与结局、随机数和模拟公式；
- 存档失败时内存态仍可继续，重新加载可能再次出现复盘，但不能阻断游戏。

### 6.4 弹窗优先级

从高到低：

1. 待处理事件；
2. 人生结局；
3. 玩家主动打开的工具；
4. 第一年度复盘。

第一年度复盘不能覆盖事件选择或结局，也不能在玩家正在使用商店、脚本等工具时抢占界面。

### 6.5 失败回退

- 推荐行动不存在或不可用：回退到当前首个可执行行动；
- 当前没有可执行行动：目标带只显示状态和危机，不显示建议命令；
- 决策日志为空：复盘使用状态变化和“尚未形成明显选择模式”的中性说明；
- 首年提前结局：只展示现有结局复盘；
- `localStorage` 不可用：维持现有中文错误提示，不暴露异常或堆栈；
- 低宽度视口：目标节点允许换行，但不能横向滚动或覆盖行动区。

## 7. 验收标准

### 7.1 产品验收

定向可用性验证使用至少 5 名符合目标画像、未参与开发的程序员。该样本只用于发现问题，不用于宣称市场统计结论。

- 5 人中至少 4 人在 45 秒内完成第一次有效行动；
- 5 人中至少 4 人完成第一年度复盘；
- 5 人中至少 3 人在无提示复述中说清一个收益和一个代价；
- 5 人中至少 3 人主动选择继续或表达重开意愿；
- 任何人出现“为什么结果和界面说的不一样”都记录为阻断问题。

在没有真实测试者前，只能声明技术验收通过，不能声明产品指标已达成。

### 7.2 自动化验收

- 阶段派生覆盖：作品集前、投递中、面试中、Offer 中、已就业、危机、首年结束；
- 推荐行动始终真实可执行；
- 旧存档不自动进入第一年流程；
- 每日挑战结果与历史行为不变；
- 第一年度复盘只自动出现一次；
- 待处理事件和结局优先级正确；
- 决策日志为空时复盘仍可渲染；
- `npm run lint` 通过；
- `npm test -- --maxWorkers=1` 通过；
- `npm run build` 通过；
- `npm run simulate` 通过；
- `npm run simulate:batch` 中 `releaseGate.passed=true` 且确定性回放率为 `1`；
- `git diff --check` 通过。

### 7.3 浏览器验收

在 390x844、768x1024、1280x800 三档视口验证：

- 主命令不被挤出关键首屏；
- 无横向溢出；
- 可见交互目标不低于 44px；
- 目标带、行动区和复盘弹窗不互相覆盖；
- 长职业名、长目标和最大数值不会撑坏布局；
- 三套主题均有可读对比度；
- 旧存档、普通新局和每日挑战各跑一次完整关键路径。

## 8. 实施顺序

1. 行为保持地迁出 `GameScreen` 和 `CareerSetupScreen`，单独提交；
2. 为第一年纯系统先写失败测试，再实现阶段、建议和复盘数据；
3. 接入启动页布局和目标带；
4. 接入第一年度复盘与幂等标记；
5. 收敛头部次级工具；
6. 跑单元、UI、构建和模拟门槛；
7. 做三档浏览器和三主题验证；
8. 完成用户可见层审计和开发复盘；
9. 代码审查通过后提交功能分支；
10. 发布前单独列出备份、影响、回退和验证，获得确认后再合入 `master`、部署和打 `v2.1` 标签。

## 9. 风险与回退

| 风险 | 等级 | 控制方式 |
|---|---|---|
| 推荐变成隐性自动玩法 | 中 | 只展示一个可解释建议，永不自动执行 |
